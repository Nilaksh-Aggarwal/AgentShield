## Conventions

- xUnit; `Method_Scenario_Expectation` names; `Assert` only (no assertion library).
- Test behaviour, not implementation details. No placeholder or coverage-only tests.
- Security, Application and Infrastructure implementations stay `internal`; `InternalsVisibleTo` (in their csproj) lets
  SecurityTests and UnitTests (Infrastructure: UnitTests only) construct them directly. ApiTests replace or add pipeline
  stages with `ConfigureTestServices` (e.g. a throwing `IThreatDetector` to test the 500 path).
- Time-dependent code takes `TimeProvider`; tests use a manual clock (timeouts, capacity windows), never the wall clock.
- ApiTests register a **test-only** `ContractProbeController` (via `AddApplicationPart` in the test factory) to drive
  every Result→HTTP path through the real pipeline without shipping demo endpoints.
- Limits enforced by Kestrel (body size) are not emulated by the in-memory TestServer; such tests call
  `UseKestrel(0)` + `StartServer()` on the factory (loopback, dynamic port).
- IntegrationTests capture Serilog events with an `ILogEventSink` registered in DI (`ReadFrom.Services`).
- AI analysis is tested with a deterministic `ScriptedAiSecurityAnalyzer` that lives in the test projects (never in
  `AgentShield.AI`) and is registered with `ConfigureTestServices`; its JSON answers go through the real strict parser.
  Timeout boundaries use a manual `TimeProvider` with timers, so they are exact and do not wait on the clock.
- The Gemini adapter is tested through the real Google.GenAI SDK against a fake `HttpMessageHandler`
  (`SecurityTests/AiAnalysis/Gemini`), and the whole composition with that fake installed as every `IHttpClientFactory`
  client's primary handler (`GeminiProviderPipelineTests`, via `ConfigureHttpClientDefaults`). Both test factories force
  `Ai:Enabled=false` and a blank `Ai:Gemini:ApiKey`, so a developer's AI settings and User Secrets never reach a test
  host (`TestHosts_NeverSeeTheDevelopersAiSettingsOrUserSecret`). **No automated test
  calls Google or uses quota.** The real-API check is a manual script,
  `scripts/gemini-smoke.ps1`, outside the test suite (no skipped tests). See
  docs/security/ai-analysis.md, section 15.
- **AI quality evaluation (Milestones 7, 7.1):** the labelled, synthetic set in `tests/Evaluation` is used twice. The
  automated `AiEvaluationSetTests` hold the dataset rules (pinned content fingerprint, tags, review flags, synthetic
  secrets) and the decision-integrity properties for every fixture without quota. The manual runner
  `tests/AgentShield.Evaluation` (ADR 0017) measures the real Gemini behaviour through the production path; its own
  behaviour is tested without any provider traffic: `EvaluationRunnerTests` (whole sessions against the real composition
  with a fake transport and its `VirtualClock`: every call recorded, deterministic Blocks never sent, resume without
  re-sending, previously failed fixtures last or excluded, timeout recorded without a response, stop at the first 429 and
  the second 503, hard cap, pre-flight before the first request, refusal of changed texts or detectors, no sensitive data
  in any artifact) and `EvaluationLogicTests` (safety limits, command line, stop rules, planner, record fields and
  serialisation, metrics, report sections, committed artifacts). See docs/security/ai-analysis.md, section 18.
- Test hosts register their own API clients (`TestApiKeys`: hashes computed in the test, independently of the API's
  code) and raise rate limits far above what any test sends; `CreateClient()` sends the `test-analyzer` key by default,
  so contract tests exercise what they always did. Security tests remove the header or configure small limits on their
  own host (`WithWebHostBuilder`, which also gives them their own in-memory limiter). `ProductionApiFactory` runs the API
  in the Production environment (no Development client or origin). Rate-limit tests use a 60 s window so a window never
  rolls over during a test; flood tests are bounded (≤ 40 requests).
- Tests that need PostgreSQL behaviour use an unreachable connection string (fast failure) today; real database tests
  should use Testcontainers when persistence lands.
- Security features must ship with adversarial cases (obfuscation, encodings, multi-step attacks) in SecurityTests.
- **Property and exhaustive tests** use a fixed seed (`new Random(seed)`) or enumerate the whole input space, so every
  run checks the same cases and a failure names the input. They compare against an oracle written from the specification,
  never against the code under test. A property that finds a defect outside the milestone's scope is not weakened: the
  defect is recorded and pinned by a test of its current, fail-closed behaviour (D-18, pinned in Milestone 8 and turned
  into an analysed-decision test when it was fixed).
- **Hand-applied mutants** check new security behaviour outside the Stryker scopes (Milestone 9: sink-failure handling,
  AI-status reduction, page-size bound, the console's AI-status echo). After restoring a mutated file, touch it and
  build with `--no-incremental`: a restored copy keeps its old timestamp, and an incremental build keeps the mutant.
- **Frontend tests** (`npm test`) test what a user sees and what a module promises (presentation functions, rendered
  text, roles), not component internals. `fetch` is stubbed with `vi.stubGlobal`; nothing reaches a server.
- **Browser checks** (`npm run test:e2e`) need `dotnet build` and `npm run build` first; they are not part of
  `dotnet test` or `npm test` because they start real servers and a browser.
- **Mutation testing** (Stryker.NET, a local dotnet tool; configs in `tests/mutation/`) checks that the tests of the
  security core fail when the code is wrong. It is run on demand, not on every build (minutes per scope). A surviving
  mutant is either killed by a test that checks real behaviour or recorded with the reason it cannot matter.

## Running

```bash
dotnet test AgentShield.slnx
dotnet test tests/AgentShield.SecurityTests
dotnet test --filter "FullyQualifiedName~ErrorResponseContractTests"

cd frontend/agentshield-web
npm test                 # unit and component tests (Vitest)
npm run build && npm run test:e2e   # browser checks against the real API (after dotnet build)

dotnet tool restore      # once: Stryker.NET from dotnet-tools.json
cd tests/mutation
dotnet stryker --config-file stryker-security.json      # Security project, SecurityTests
dotnet stryker --config-file stryker-ai-capacity.json   # capacity gate, circuit breaker, token budget; UnitTests
dotnet stryker --config-file stryker-api-boundary.json              # authentication, rate limiting; ApiTests
dotnet stryker --config-file stryker-api-boundary-integration.json  # the same code; IntegrationTests
# Milestone 10, agent action authorization (one test project per run):
dotnet stryker --config-file stryker-agent-security.json        # classifier, policy, authorizer, catalogue; SecurityTests
dotnet stryker --config-file stryker-agent-domain.json          # names, profile, verdict, event; UnitTests
dotnet stryker --config-file stryker-agent-application.json     # use case, validator, activity record; UnitTests
dotnet stryker --config-file stryker-agent-infrastructure.json  # agent directory, audit sink; UnitTests
dotnet stryker --config-file stryker-agent-api.json             # permission, policy, client registry; ApiTests
# Milestone 11, tool gateway (one test project per run):
dotnet stryker --config-file stryker-gateway-security.json          # execution authority, argument policy; SecurityTests
dotnet stryker --config-file stryker-gateway-domain.json            # grant, outcome, lifecycle, tool types; UnitTests
dotnet stryker --config-file stryker-gateway-application.json       # gateway use case, validator, activity; UnitTests
dotnet stryker --config-file stryker-gateway-infrastructure.json    # tool, audit sink, gateway identities; UnitTests
dotnet stryker --config-file stryker-gateway-api.json               # controller, permission, client registry; ApiTests
# Milestone 12, activity summary and the D-21 change (the console was checked with hand-applied mutants):
dotnet stryker --config-file stryker-attacklab-application.json      # summary use case, ToolGateway; UnitTests
# Milestone 13, human approval and input binding (ToolGateway.ExecuteAsync is covered by hand-applied mutants: Stryker
# cannot compile any mutant inside it):
dotnet stryker --config-file stryker-approval-domain.json          # approval, binding, approval and gateway events; UnitTests
dotnet stryker --config-file stryker-approval-application.json     # gateway, approval use cases, EventSinks, input recorder; UnitTests
dotnet stryker --config-file stryker-approval-infrastructure.json  # approval store, input context store; UnitTests
dotnet stryker --config-file stryker-approval-security.json        # execution authority with the approval check; SecurityTests
node merge-reports.mjs StrykerOutput/<api run>/reports/mutation-report.json StrykerOutput/<integration run>/reports/mutation-report.json
```

The API boundary scope runs once per test project and the reports are merged (ADR 0018): with both test projects in
one run, Stryker reported mutants as surviving that ApiTests kill on their own. Each surviving mutant is classified as a
real test gap (a test is added and shown to fail against the mutant), equivalent, redundant or unreachable, or a tooling
limitation; the latest classification is in docs/security/test-coverage-summary.md.
