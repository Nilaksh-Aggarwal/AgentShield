# Attack surface

Everywhere an attacker can interact with AgentShield, what they control there, what protects it, what happens when that
protection is hit, and the evidence. As of 2026-10-07 (Milestone 13); built from the code and tests only. Request order:
[security architecture](security-architecture.md). Guarantees: [security invariants](security-invariants.md).
Detection limits: [coverage matrix](security-coverage-matrix.md). Known issues: [defect matrix](defect-matrix.md).

Attackers considered: an anonymous network client; an authenticated client (a compromised or malicious agent, or a
caller relaying untrusted text); a hijacked agent proposing tool actions through its runtime, or a compromised runtime, or an agent calling the tool
gateway with its own credential, or replaying, transferring or forging approvals; a client holding the approval
permission (a person's console);
a manipulated AI model (via the content it reads); a misbehaving or impersonated provider endpoint. Operators are
trusted, but their configuration is validated.

## Highest remaining exposure

0. **Only one tool is enforced (Milestone 11).** The tool gateway runs `knowledge.lookup` only on Allow, with the agent
   taken from its key, its arguments checked and a single-use grant. For every other tool AgentShield is still a decision
   point: a runtime that does not ask, ignores the answer, or executes on Review, a timeout or a 5xx bypasses the
   boundary; at `/agent/actions/authorize` a runtime chooses the agent ID among its bound agents. Since Milestone 13 a
   gateway call can be bound to its input's analysis, but only if it references it: a runtime that omits the reference
   is decided on the action alone ([tool-gateway.md](tool-gateway.md), sections 14 and 17).
0a. **Approvals are per process and in memory (Milestone 13).** A restart forgets every approval (fail-safe: nothing is
   approved). 1,000 open approvals fill the store, after which new holds fail with 500 until approvals finish or expire
   (bounded by the `Standard` rate limit per client). The approver sees metadata only, not the arguments.

1. **Detection breadth.** Paraphrased, non-English, indirect and multi-turn attacks pass the deterministic rules (recall
   0.38 on the synthetic set); with AI off they are Allowed. This is the main way an attacker gets an unsafe Allow, and
   it is a capability limit, not a defect.
2. **Unauthenticated volume.** Anonymous requests are rejected cheaply but not rate limited: log volume and CPU for hash
   lookups are attacker-controlled. A reverse proxy or a pre-authentication limit is needed in production.
3. **AI signal denial.** Content that makes the model slow can open the circuit, so AI-eligible inputs are Review for
   the open period: fail-safe, but an operational load.
4. **Audit durability.** Security events live only in logs; a sink failing inside Serilog loses entries silently (the
   decision metric still counts them). The activity history (Milestone 9) does not change this: it is in memory, lost
   on restart and per process.
5. **Frontend CSP.** The console has no Content-Security-Policy of its own.

## Not an attack surface today

Tools other than `knowledge.lookup` and their arguments and results (nothing else runs through AgentShield), the
protected agent's output, multi-turn state, agent memory, document or RAG sources, persisted security events (no database
entities exist), and any endpoint other than `POST /api/v1/firewall/analyze`, `POST /api/v1/agent/actions/authorize`,
`POST /api/v1/agent/tools/execute`, `GET /api/v1/agent/approvals`, `POST /api/v1/agent/approvals/{approvalId}/approve`
and `/deny`, `GET /api/v1/activity`, `GET /api/v1/activity/summary` and the health probes. The Attack Lab adds no endpoint: it calls the firewall and the gateway like any client.
